# 키오스크 길잡이 구현계획서

2026-10-28 작성 · 2026-11-18 중간발표 기준으로 갱신 · 이동건, 정윤서

1장은 Sprint 2(11~13주) MVP의 기능·역할별 작업·일정·위험을, 2장은 Sprint 3 이후 완성본의 방향을 정리한다. 진행 상태는 11월 18일 중간발표 자료([중간발표/](중간발표/))를 기준으로 했다.

## 1. MVP 구현 계획 (Sprint 2)

Sprint 2까지 **먼저 주문할 메뉴를 목표로 정하고(말하기·글자·메뉴 화면 찍어서 고르기), 그다음에는 찍기 버튼 없이 카메라를 비추기만 하면 실시간 화면 위 버튼 표시와 음성 안내를 받으며 주문을 끝까지 마치는 버전**을 만든다.

### 완료 기준 (시연 시나리오)

실제 매장 키오스크 앞에서 "아이스 아메리카노 한 잔 포장"을 말하고 시작하기를 누른 뒤 휴대폰을 비추면, 커피 → 아메리카노 → 아이스 → 포장 → 결제하기까지 버튼 표시와 음성 안내가 이어지고 완료 화면이 나온다. 동시에 평가 데이터로 잰 정확도 1차 결과를 발표한다.

### 현재 상태 (11월 18일, 중간발표)

**주문 안내 흐름은 끝까지 동작하고 kiosson.vercel.app에 배포했다.** 목표 입력(말하기·글자·메뉴 화면 찍어서 고르기), 실시간 카메라와 화면 변화 감지 자동 전송, 2단계 안내(판단 → 위치 찾기)와 사진 위 1·2·3 상자, 음성 안내(같은 안내는 한 번만 읽기), 누른 버튼 기록, 피드백 저장(Neon, 사진은 저장 안 함)이 동작한다.

| 영역 | 상태 |
| --- | --- |
| AI 서버 | 3060 PC의 Ollama를 임시 Cloudflare Tunnel로 연결했다. 주소가 켤 때마다 바뀌어 고정 주소가 필요하다. |
| 1차 측정 | 평가 스크립트·라벨링 도구를 만들고 49문항으로 7B(프롬프트만)를 쟀다: 버튼 이름 73.5%, 위치 57.1%, 평균 약 3초. |
| 파인튜닝 | 메가커피 데이터로 3B QLoRA 1차 학습 중이다(학습·변환·연결 과정 확인용). |
| 틀린 안내 거르기 | 상자 부분을 잘라 그 버튼이 맞는지 다시 묻는 검증 단계를 실험 중이다. 틀린 안내 22~23개 → 5~12개로 줄었지만, 맞는 안내도 약 8개가 걸러져 조각 글자를 읽어 이름과 비교하는 방식을 시험한다. |

남은 큰 일은 **다른 매장 데이터 수집과 재학습, AI 서버 고정 주소, 실기기 테스트**다. 첫 버전의 찍기 버튼·사진 업로드 방식은 실시간 안내로 대체하면서 앱에서 뺐다.

### MVP 범위 ([기획서](기획서/) 9.2 기준)

- **필수**: 실시간 카메라 버튼 안내(문구 + 위치), 음성 입출력, Vercel 배포, 정확도 1차 측정
- **권장**: 피드백 저장, 틀린 안내 거르기(검증 단계)
- **앞당김**: LoRA 파인튜닝. 처음에는 Sprint 3에 하려 했으나, 7B 1차 측정 결과가 낮아 Sprint 2 중에 시작한다(아래 "모델 선정 변경").
- **이번에 안 함**: 개선 전후 비교(Sprint 3), 목표 없이 시작하는 둘러보기(목표 필수로 정하면서 뺌)

### 모델 선정 변경 (7B 프롬프트만 → 3B + LoRA)

처음 계획은 Qwen2.5-VL 7B를 학습 없이 프롬프트만으로 쓰는 것이었다. 선정 경과는 아래와 같다.

1. **7B를 프롬프트만으로 쓴 성능이 기대보다 낮았다.** 평가 데이터 49문항 1차 측정에서 버튼 이름 73.5%, 위치 정확도 57.1%로 둘 다 목표 90%에 못 미쳤다. 이름과 위치가 둘 다 맞은 것은 53~55%였다.
2. **그래서 파인튜닝을 하기로 바꿨다.** 프롬프트 개선만으로는 한계가 있다고 보고, 직접 모은 키오스크 데이터로 LoRA 학습을 한다. Sprint 3 계획을 앞당긴 것이다.
3. **7B 파인튜닝은 지금 상황에서는 불가능하다고 판단했다.** 학습 PC의 RTX 3060 12GB에서 7B는 4비트 QLoRA도 메모리가 빠듯하고 16비트 LoRA는 불가능하다. 3B는 QLoRA에 여유가 있다([AI_구현_가이드라인.md](AI_구현_가이드라인.md) 4.1).
4. **결론: 3B + LoRA.** 모델 자체의 성능은 한 단계 낮추는 대신, 우리 데이터로 직접 학습할 수 있는 크기를 골랐다. 이 선택이 맞는지는 학습에 쓰지 않은 매장 사진으로 **3B 원본 · 3B + LoRA · 7B 원본**을 같은 표에 놓고 확인한다. 7B 원본 결과가 기준선이다.

### 모델 출처 확정: Hugging Face 원본 (11월 18일)

Qwen 모델은 **Hugging Face의 원본 [`Qwen/Qwen2.5-VL-3B-Instruct`](https://huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct)를 받아서 쓰는 것으로 확정했다.**

| 단계 | 쓰는 모델 |
| --- | --- |
| 학습 | HF 원본 위에 QLoRA 학습 |
| 정확도 평가(3B 원본 vs 3B + LoRA) | HF 원본과 HF 원본 + LoRA 어댑터(transformers, BF16) |
| 서비스 | 어댑터를 HF 원본에 합친 모델을 Ollama에 등록(GGUF). 안 되면 vLLM |

- 이유: Ollama 라이브러리의 `qwen2.5vl:3b`는 4비트로 줄인 변환본이라 학습 기준과 다르고, 11월 18일 점검에서 Ollama 0.40.15·0.40.16이 사진을 한 번 처리한 뒤 `888…`만 내는 버그가 있어 정확도를 잴 수 없었다. 학습과 평가를 같은 원본에서 해야 전후 비교가 맞다.
- Ollama 라이브러리 모델은 파인튜닝 모델을 올리기 전까지 서비스가 돌아가는지 확인하는 용도로만 쓴다.
- 합치기 → Ollama 등록 → 앱 연결 순서는 [파인튜닝_모델_적용_가이드.md](파인튜닝_모델_적용_가이드.md)에 정리했다.

### 두 사람의 접점

웹과 AI는 [lib/guide.ts](../lib/guide.ts)의 요청·응답 형식으로만 만난다. 지금까지 바뀐 점은 **목표(`goal`)가 필수가 된 것**(빈 목표는 `/api/guide`가 거절), 프롬프트 문구를 사진이 아닌 실시간 카메라 장면 기준으로 고친 것, 그리고 목표를 고르기 위한 **메뉴 읽기**(`buildMenuMessages`·`menuSchema`·`parseMenu`, `/api/menu`, 응답은 `{ items: [{ name, price }], message }`)를 더한 것이다. Ollama 호출은 `lib/ollama.ts`로 모아 두 API가 함께 쓴다. 남은 일은 검증 단계(A8)에서 걸러진 안내를 웹이 처리하는 것(W11)이다. 형식을 바꿀 때는 먼저 알리고 각자 `feat/ai`, `feat/web` 브랜치에서 개발한 뒤 Pull Request로 합친다.

AI 서버나 모델이 바뀌어도 코드는 그대로 두고 환경변수만 바꾼다: `OLLAMA_URL`(Tunnel 주소), `OLLAMA_MODEL`, `KIOSK_AI_MOCK=0`. Tunnel은 `--http-host-header="localhost:11434"`를 붙여 실행한다. 파인튜닝 모델을 올리면 `OLLAMA_MODEL`만 새 이름(예: `qwen2.5vl-kiosk:3b`)으로 바꾼다.

틀린 안내 거르기는 검증 단계(A8)로 한다. 검증에서 걸러진 안내는 버튼 목록이 빈 채로 오고, 웹은 상자를 띄우지 않고 다음 장면을 다시 분석한다.

**공동**

- **데이터 수집(11월 말까지 매장 10곳·사진 200장 이상).** 지금 데이터는 49문항·사진 9장(사진 36문항, 영상 장면 13문항)으로 메가커피 한 브랜드의 키오스크 2종뿐이고, 1차 학습에 써서 학습 후 평가에는 쓸 수 없다.
  - 수집: 매장 허락을 받고 주문 처음부터 결제까지 영상으로 찍은 뒤, 화면이 바뀔 때마다 장면을 이미지로 추출한다. 두 사람이 매장 5곳 이상씩, 다른 업종 키오스크를 포함하고 각도·반사·흐림을 섞는다.
  - 정리: 라벨링 도구로 정답 버튼을 표시하고 서로 교차 검토한다. 한 화면에 목표 여러 개를 붙여 문항을 늘리고, **매장 단위로 학습용·평가용을 나눈다.** 얼굴·카드 정보가 찍힌 사진은 뺀다.
- **흐린 장면 거르기:** 약한 흐림에도 정답이 절반 이하로 떨어진다. 선명한 프레임만 전송한다.
- **실패할 때 안내:** 검증에서 걸러지면 상자를 숨기고, 계속 실패하면 "조금 더 가까이 비춰 주세요"라고 안내한다(W8, W11).
- 시연 리허설(실제 매장 또는 키오스크 화면 사진을 띄운 모니터), 시연 전날 점검 목록, 대체용 시연 영상 녹화

### 실행 방법

```bash
cp .env.example .env.local     # OLLAMA_URL, OLLAMA_MODEL, DATABASE_URL 채우기
npm run dev                    # AI 없이 화면만 볼 때: .env.local에 KIOSK_AI_MOCK=1
```

- 피드백 저장 테이블: Neon 콘솔 SQL Editor에서 `db/schema.sql` 실행
- 휴대폰 카메라는 HTTPS에서만 열린다. 실기기 테스트는 Vercel 배포 주소나 Tunnel 주소로 한다.

### 알려진 한계

- 화면 변화 기준값(`app/live-camera.ts`의 `MOVING`, `CHANGED`)은 추정치라 실제 매장에서 조정해야 한다.
- 목업 모드는 정해진 답만 돌려주므로 실시간 모드에서는 첫 단계 안내만 반복된다. 단계 진행 확인은 실제 모델로 한다.

## 2. 완성본 구현 계획 (Sprint 3 이후까지)

완성본은 **휴대폰을 흔들어도 상자가 버튼에 붙어 따라가고, 손가락이 버튼에 닿으면 알아서 다음 단계로 넘어가는 길잡이**다. 여기에 모델 개선과 비교 실험, 메뉴 읽어 주기·연습·다국어 기능을 더해 "처음 보는 키오스크도 혼자 주문"을 수치로 보여 준다.

### 안내 경험

| 기능 | 설명 |
| --- | --- |
| 버튼을 따라가는 상자 | OpenCV.js 특징점 추적으로 휴대폰이 움직여도 빨간 상자가 버튼 위에 그대로 붙어 있다. AI는 화면이 바뀔 때만 부르고, 매 프레임은 휴대폰이 처리한다. |
| 대상 버튼만 남기는 강조 | 화면 전체를 어둡게 덮고 눌러야 할 버튼만 밝게 뚫어 보인다(GuideMe 방식). |
| 손가락 확인과 자동 진행 | MediaPipe 손 추적으로 손가락이 목표 버튼에 닿은 뒤 화면이 바뀌면 다음 단계로 넘어간다. 다른 버튼에 손이 가면 "그 버튼이 아니에요"라고 미리 알려 준다. |
| 비추는 방향 음성 안내 | 화면이 잘리거나 흐리면 "조금 더 왼쪽으로", "조금 더 가까이"처럼 소리로 알려 준다. 저시력 사용자도 혼자 비출 수 있다. |
| 메뉴 읽어 주기 | 무엇을 주문할지 정하기 어려울 때 화면의 메뉴와 가격을 읽어 준다. "이걸로 할게요"라고 말하면 그 메뉴가 목표가 되어 바로 주문 안내로 넘어간다. 목표를 정한 뒤 안내한다는 원칙은 그대로 둔다. |
| 안내 중 대화 | "얼음 적게 돼요?", "포장 말고 매장으로 바꿀게요"처럼 말하면 화면을 보고 답하거나 목표를 고친다. (목표 바꿔 말하기는 MVP에 들어감) |
| 다국어 안내 | 영어를 먼저 완성하고 중국어·일본어로 넓힌다. 한국어 키오스크를 사용자의 언어로 설명한다. |
| 집에서 미리 연습 | 매장 키오스크 사진으로 집에서 같은 안내를 받으며 연습해, 매장에서 뒷사람 눈치 부담을 줄인다. |
| 나에게 맞춘 설정 | 글씨 크기, 고대비 화면, 말하는 속도를 기억한다. 홈 화면에 추가하는 웹 앱(PWA)과 QR코드로 바로 연다. |

| 글자 인식(OCR) 결합 | OCR로 화면 글자와 위치를 정확히 뽑고, AI는 누를 버튼 글자만 고르게 해 위치 정확도를 높인다. 정확도가 목표에 못 미칠 때 시도한다. |
| 같은 화면 캐시 | 방금 본 화면과 같으면 AI를 다시 부르지 않고 결과를 재사용해 주문 1회당 호출을 5\~10회로 줄인다. |
| 피드백으로 개선 | [틀렸어요]가 눌린 장면을 모아 실패 유형을 분류하고, 프롬프트와 학습 데이터에 되돌린다. 결과는 간단한 관리 화면에서 본다. |

### 도전 목표

| 지표 | MVP 목표 | 완성본 도전 목표 |
| --- | --- | --- |

| 위치 정확도 | 90% | 90% |
| 화면 변화 후 새 안내까지 | 5초 | 3초 |

### 더 나아갈 수 있다면

- **다른 무인기기**: 무인민원발급기, 병원 접수기, 주차 정산기에서도 같은 방식으로 안내해 본다.
- **휴대폰 안의 작은 모델**: 화면 단계 판단처럼 가벼운 일은 휴대폰에서 처리해 서버 왕복을 줄인다.
- **키오스크 종류 기억**: 한 번 안내한 키오스크의 화면 구조를 저장해, 다음 사용자에게 더 빠르고 정확하게 안내한다.
- **공개 데이터셋**: 개인정보를 지운 키오스크 화면·정답 버튼 데이터를 접근성 연구용으로 정리한다.
