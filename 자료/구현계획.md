# 키오스크 길잡이 구현계획서

2026-10-28 · 이동건, 정윤서

1장은 Sprint 2(11~12주) MVP의 기능·역할별 작업·일정·위험을, 2장은 Sprint 3 이후 완성본의 방향을 정리한다.

## 1. MVP 구현 계획 (Sprint 2)

Sprint 2까지 **찍기 버튼 없이 카메라를 비추기만 하면, 실시간 화면 위 버튼 표시와 음성 안내를 받으며 주문을 끝까지 마치는 버전**을 만든다.

### 완료 기준 (시연 시나리오)

실제 매장 키오스크 앞에서 "아이스 아메리카노 한 잔 포장"을 말하고 시작하기를 누른 뒤 휴대폰을 비추면, 커피 → 아메리카노 → 아이스 → 포장 → 결제하기까지 버튼 표시와 음성 안내가 이어지고 완료 화면이 나온다. 동시에 평가 데이터로 잰 정확도 1차 결과를 발표한다.

### 현재 상태 (10월 28일)

웹은 실시간 안내 흐름이 완성되어 Vercel에 배포했다. 목표 입력(말하기·글자), 실시간 카메라, 자동 장면 선택, 영상 위 빨간 상자, 음성 안내, 누른 버튼 기록, 피드백 저장(Neon)이 동작한다. AI 서버가 연결되기 전까지는 정해진 답을 돌려주는 **목업 모드**(`KIOSK_AI_MOCK=1`)로 화면 흐름을 확인한다.

남은 큰 일은 **AI 서버 연결(Tunnel), 확신도, 정확도 측정**이다. 첫 버전의 찍기 버튼·사진 업로드 방식은 실시간 안내로 대체하면서 앱에서 뺐다.

### MVP 범위 (기획서 9.2 기준)

- **필수**: 실시간 카메라 버튼 안내(문구 + 위치), 음성 입출력, Vercel 배포, 정확도 1차 측정
- **권장**: 피드백 저장, 확신도 판단
- **이번에 안 함**: LoRA 파인튜닝, 개선 전후 비교(Sprint 3), 목표 없이 시작하는 둘러보기(목표 필수로 정하면서 뺌)

### 두 사람의 접점

웹과 AI는 [lib/guide.ts](../lib/guide.ts)의 요청·응답 형식으로만 만난다. 지금까지 바뀐 점은 **목표(`goal`)가 필수가 된 것**(빈 목표는 `/api/guide`가 거절)과 프롬프트 문구를 사진이 아닌 실시간 카메라 장면 기준으로 고친 것이다. 남은 변경은 응답에 **확신도**를 더하는 것 하나다. 이 형식을 먼저 확정하고 각자 `feat/ai`, `feat/web` 브랜치에서 개발한 뒤 Pull Request로 합친다.

AI 서버가 준비되면 코드는 그대로 두고 환경변수만 바꾼다: `OLLAMA_URL`(Tunnel 주소), `OLLAMA_MODEL`, `KIOSK_AI_MOCK=0`. Tunnel은 `--http-host-header="localhost:11434"`를 붙여 실행한다.

확신도(A3)는 응답에 `confidence: "high" | "medium" | "low"`를 더하고, 웹은 `low`면 상자를 띄우지 않고 다음 장면을 다시 분석하는 방식으로 제안한다. 두 번 질의해 비교하는 방법은 응답 시간이 두 배가 되므로 1차 측정 결과를 보고 정한다.

### 실행 방법

```bash
cp .env.example .env.local     # OLLAMA_URL, OLLAMA_MODEL, DATABASE_URL 채우기
npm run dev                    # AI 없이 화면만 볼 때: .env.local에 KIOSK_AI_MOCK=1
```

- 피드백 저장 테이블: Neon 콘솔 SQL Editor에서 `db/schema.sql` 실행
- 휴대폰 카메라는 HTTPS에서만 열린다. 실기기 테스트는 Vercel 배포 주소나 Tunnel 주소로 한다.

### 알려진 한계

- 화면 변화 기준값(`app/live-camera.ts`의 `MOVING`, `CHANGED`)은 추정치라 실제 매장에서 조정해야 한다.
- 목업 모드는 정해진 답만 돌려주므로 실시간 모드에서는 첫 단계 안내만 반복된다. 단계 진행 확인은 실제 모델로 한다.

## 2. 완성본 구현 계획 (Sprint 3 이후까지)

완성본은 **휴대폰을 흔들어도 상자가 버튼에 붙어 따라가고, 손가락이 버튼에 닿으면 알아서 다음 단계로 넘어가는 길잡이**다. 여기에 모델 개선과 비교 실험, 메뉴 읽어 주기·연습·다국어 기능을 더해 "처음 보는 키오스크도 혼자 주문"을 수치로 보여 준다.

### 안내 경험

| 기능 | 설명 |
| --- | --- |
| 버튼을 따라가는 상자 | OpenCV.js 특징점 추적으로 휴대폰이 움직여도 빨간 상자가 버튼 위에 그대로 붙어 있다. AI는 화면이 바뀔 때만 부르고, 매 프레임은 휴대폰이 처리한다. |
| 대상 버튼만 남기는 강조 | 화면 전체를 어둡게 덮고 눌러야 할 버튼만 밝게 뚫어 보인다(GuideMe 방식). |
| 손가락 확인과 자동 진행 | MediaPipe 손 추적으로 손가락이 목표 버튼에 닿은 뒤 화면이 바뀌면 다음 단계로 넘어간다. 다른 버튼에 손이 가면 "그 버튼이 아니에요"라고 미리 알려 준다. |
| 비추는 방향 음성 안내 | 화면이 잘리거나 흐리면 "조금 더 왼쪽으로", "조금 더 가까이"처럼 소리로 알려 준다. 저시력 사용자도 혼자 비출 수 있다. |
| 메뉴 읽어 주기 | 무엇을 주문할지 정하기 어려울 때 화면의 메뉴와 가격을 읽어 준다. "이걸로 할게요"라고 말하면 그 메뉴가 목표가 되어 바로 주문 안내로 넘어간다. 목표를 정한 뒤 안내한다는 원칙은 그대로 둔다. |
| 안내 중 대화 | "얼음 적게 돼요?", "포장 말고 매장으로 바꿀게요"처럼 말하면 화면을 보고 답하거나 목표를 고친다. (목표 바꿔 말하기는 MVP에 들어감) |
| 다국어 안내 | 영어를 먼저 완성하고 중국어·일본어로 넓힌다. 한국어 키오스크를 사용자의 언어로 설명한다. |
| 집에서 미리 연습 | 매장 키오스크 사진으로 집에서 같은 안내를 받으며 연습해, 매장에서 뒷사람 눈치 부담을 줄인다. |
| 나에게 맞춘 설정 | 글씨 크기, 고대비 화면, 말하는 속도를 기억한다. 홈 화면에 추가하는 웹 앱(PWA)과 QR코드로 바로 연다. |

### AI와 성능

| 항목 | 설명 |
| --- | --- |
| 프롬프트 개선 | 화면 단계 판단 → 버튼 선택 2단계 질의, few-shot 예시, 이미지 보정(회전·밝기) |
| LoRA 파인튜닝 | 수집한 키오스크 데이터로 학습하고, 학습에 쓰지 않은 매장으로 전후 성능을 비교한다. |
| 모델 비교 실험 | Qwen2.5-VL 7B·3B, 상용 API(Gemini·GPT·Claude 계열), 더 최신 소형 VL 모델(확인 필요)을 같은 평가 데이터로 비교해 정확도·응답 시간·비용 표를 만든다. |
| 글자 인식(OCR) 결합 | OCR로 화면 글자와 위치를 정확히 뽑고, AI는 누를 버튼 글자만 고르게 해 위치 정확도를 높인다. 정확도가 목표에 못 미칠 때 시도한다. |
| 같은 화면 캐시 | 방금 본 화면과 같으면 AI를 다시 부르지 않고 결과를 재사용해 주문 1회당 호출을 5\~10회로 줄인다. |
| 피드백으로 개선 | [틀렸어요]가 눌린 장면을 모아 실패 유형을 분류하고, 프롬프트와 학습 데이터에 되돌린다. 결과는 간단한 관리 화면에서 본다. |

### 더 나아갈 수 있다면

- **다른 무인기기**: 무인민원발급기, 병원 접수기, 주차 정산기에서도 같은 방식으로 안내해 본다.
- **휴대폰 안의 작은 모델**: 화면 단계 판단처럼 가벼운 일은 휴대폰에서 처리해 서버 왕복을 줄인다.
- **키오스크 종류 기억**: 한 번 안내한 키오스크의 화면 구조를 저장해, 다음 사용자에게 더 빠르고 정확하게 안내한다.
- **공개 데이터셋**: 개인정보를 지운 키오스크 화면·정답 버튼 데이터를 접근성 연구용으로 정리한다.
