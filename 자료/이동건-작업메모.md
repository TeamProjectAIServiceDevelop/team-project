## 4. 알아낸 것 (잊지 말 것)

- **Ollama는 보낸 사진 크기와 상관없이 이미지를 안쪽에서 약 100만 픽셀로 바꾸고, 모델은 그 크기 기준 좌표를 낸다.** 작은 사진을 그대로 보내면 좌표가 어긋나 위치 정확도가 0%가 된다. 28의 배수이면서 98만 픽셀 이하(Ollama 상한 1,003,520)로 맞추면 좌표가 맞는다. 정윤서가 `app/frame.ts`에 같은 방식(내림)을 이미 넣었다.
- **사진 크기가 28픽셀만 달라도 모델 답이 달라진다.** 평가도 반드시 앱과 같은 방식(내림)으로 보내야 점수가 앱의 정확도를 뜻한다. 같은 사진·같은 코드는 같은 결과가 나온다(결정적).
- **3B는 이 PC의 Ollama 0.40.12에서 구조화 출력이 중간부터 깨진다**(`Unexpected empty grammar stack`). 한 번 실패하면 이후 요청도 전부 실패한다. 당분간 7B를 쓴다. Ollama를 최신으로 올리면 풀리는지는 아직 확인 못 했다.
- 프롬프트에 "상자가 없으면 다시 비추라고만 말해라"를 넣어도 모델이 따르지 않았다(16문항 중 1개). 그래서 코드가 고정 문구를 정한다.
- 흐림에 약하다. 약한 흐림만 줘도 정답이 반 이하로 떨어진다. 선명한 프레임만 AI에 보내는 것(웹 쪽)이 가장 확실한 대책이다.
- 2단계(판단 → 위치 찾기)는 약 4초(생성 시간이 대부분)다. 출력을 줄이는 것은 효과가 8% 정도라 적용하지 않았다.

  - 여백은 25%가 10%보다 낫다(조각이 너무 작으면 글자를 더 못 읽는다).
  - 실험 스크립트는 저장소에 넣지 않았다. 1·2단계를 앱과 같이(98만 픽셀, 28의 배수 내림) 돌린 뒤 첫 상자를 여백 10%/25%로 잘라 `{text}` 스키마로 읽게 하고, 정규화한 글자에 버튼 이름(앞의 (ICE)/(HOT)은 빼도 됨)이 들어 있는지로 판정했다.

**파인튜닝 (2026-11-18 시작)** — 목표는 문장 답이 아니라 앱의 버튼 이름·위치 정확도를 올리는 것

- 집에서 만든 `키오스크_파인튜닝.zip`(LLaMA-Factory 가이드, 학습 485/평가 54개, 사진 22장)은 답이 문장이고 버튼 상자 좌표가 없다. 그대로는 앱의 1단계(JSON)·2단계(`bbox_2d`)를 가르칠 수 없어서, 22장에 상자를 붙이고 앱과 같은 질문·답 형식으로 다시 만들어야 한다. 학습 결과(어댑터, 점수)는 집 PC에만 있다.
- **1단계: 학습 결과를 Ollama에 넣는 길 확인 (끝남)**
  - Ollama 0.40.12는 `ADAPTER`(LoRA)를 거부한다: `LoRA adapters are no longer supported`. safetensors에서 바로 만드는 것도 Qwen2.5-VL은 지원 목록에 없다.
  - 되는 길: LoRA를 원본에 합침(`finetune/merge_lora.py`, 샤드 하나씩 처리해서 RAM 16GB로 7B도 가능) → llama.cpp `convert_hf_to_gguf.py`로 언어 모델과 `--mmproj` 비전 부분을 각각 GGUF로 → Ollama에 함께 들어 있는 `lib/ollama/llama-quantize.exe`로 Q4_K_M → Modelfile에 `FROM 모델.gguf`, `FROM mmproj.gguf` 두 줄과 기존 qwen2.5vl의 TEMPLATE을 넣고 `ollama create`. 3B로 끝까지 해 봤고, Ollama가 비전 모델(projector 포함)로 인식했다.
  - **3B는 이 Ollama에서 사진이 들어가면 "8888…"만 낸다.** 받은 `qwen2.5vl:3b`도 변환한 것도 똑같다(위치 찾기 49문항 중 47개 출력이 글자까지 같음). 같은 GGUF를 Ollama에 들어 있는 `llama-server.exe`로 직접 돌리면 정상으로 답한다. 즉 변환은 맞고, 문제는 Ollama의 3B 실행이다. 예전에 본 3B 구조화 출력 오류도 같은 원인일 가능성이 크다.
    - (11-26 추가) Ollama에 든 `llama-server.exe`는 GPU 라이브러리를 못 찾아 CPU로 돈다. CPU라서 정상이었던 것이고, 원인은 f16으로 변환한 mmproj였다. f32로 바꾸면 Ollama에서도 정상이다(아래 "3B 버튼 학습").
  - 그래서 3B를 쓰려면 Ollama 대신 llama-server(OpenAI 호환 API, `--lora`로 어댑터를 합치지 않고 붙일 수도 있음)를 쓰고 `lib/ollama.ts`를 바꿔야 한다.
  - **7B는 변환해도 된다.** 원본 7B(Hugging Face 캐시 `C:\Users\User\.cache\huggingface`)에 0 LoRA를 합쳐 같은 순서로 넣은 `kiosk-7b-conv`와 받은 `qwen2.5vl:7b`를 앱의 1·2단계로 49문항 비교했다.

    | | 이름 | 위치 | 둘 다 | 평균 |
    | --- | --- | --- | --- | --- |
    | `qwen2.5vl:7b` (받은 것) | 36 | 29 | 28 | 3.7초 |
    | `kiosk-7b-conv` (변환) | 36 | 32 | 30 | 3.6초 |

    답이 문항마다 똑같지는 않다(버튼 이름 43/49 같음). 변환한 모델은 Ollama 안에서 llama.cpp 엔진으로 돌기 때문이다. 좌표가 어긋나지는 않았고 점수는 같거나 조금 높다. 학습 후 비교의 기준선은 **`kiosk-7b-conv`(둘 다 30/49)**로 잡는다. 같은 엔진끼리 비교해야 학습 효과만 보인다.
  - 변환에 쓴 것: llama.cpp 저장소의 `convert_hf_to_gguf.py`(transformers, gguf 필요. 최신 transformers는 이 PC의 torch와 충돌해서 peft를 쓰지 않고 `merge_lora.py`로 직접 합쳤다), Ollama에 들어 있는 `llama-quantize.exe`. 디스크는 원본 16GB + 합친 것 16GB + f16 GGUF 15GB가 잠깐 필요하다.

## 7. 결과 읽는 법

- `npm run eval` 출력에서 **"버튼 안내 정확도"**는 AI가 말한 버튼 이름이 정답과 같은 비율이고, **"위치 정확도"**는 AI 상자의 중심이 정답 상자 안에 있는 비율이다. 둘은 따로 센다. 사용자에게는 둘 다 맞아야 길 안내가 된다.
