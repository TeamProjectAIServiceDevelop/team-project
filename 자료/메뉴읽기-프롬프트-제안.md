# 메뉴 읽기 프롬프트 제안 (A2)

2026-11-04 · 이동건 → 정윤서

`feat/web`의 `buildMenuMessages`(`lib/guide.ts`)를 실제 모델(Qwen2.5-VL 7B)로 시험해 보니, 메뉴 화면 6장 중 정상으로 읽은 것이 1장뿐이었다. 프롬프트를 고쳤더니 6장 중 5장을 거의 다 읽었다. 이 문서는 시험 결과와 바꿀 문구를 정리한 것이다.

## 1. 지금 프롬프트의 문제

사진: 메가엠지씨커피 키오스크 메뉴 화면 6장(`eval/data/mega/images/`의 001, 002, 003, 004, 006, 008). 사진을 약 110만 픽셀로 맞춰 보냈다.

| 사진 | 결과 |
| --- | --- |
| 001, 004 | `items`가 비었고, 안내문에 "메뉴 화면을 다시 찍어 달라고 부탁합니다"라는 지시문을 그대로 베낌 |
| 002, 008 | `items`는 비었는데 메뉴 이름을 전부 안내문(`message`)에 써 버림 |
| 003 | 40초 걸리고 형식이 깨져 `parseMenu`가 null |
| 006 | 12개 중 10개, 이름 일부 깨짐 |

웹은 `items`로 선택 목록을 만들기 때문에, 이대로면 "메뉴 화면을 찍어 목표 고르기"가 거의 동작하지 않는다.

원인은 두 가지로 본다.

- "메뉴가 보이지 않거나 사진이 흐리면 items를 빈 배열로 두라"는 문구가 너무 쉽게 발동한다.
- `message`에 무엇을 써야 하는지가 모호해서 메뉴 이름을 나열한다.

## 2. 바꾼 프롬프트의 결과

같은 사진, 같은 모델이다.

| 사진 | 읽은 메뉴 수 | 시간 |
| --- | --- | --- |
| 001 | 9 / 9 | 6.3초 |
| 002 | 12 / 12 | 7.4초 |
| 003 | 11 / 12 | 7.2초 |
| 004 | 12 / 12 | 6.7초 |
| 006 | 12 / 12 | 7.3초 |
| 008 | 8 / 10 | 5.3초 |

- 가격은 정확했다.
- 이름은 대부분 맞지만 글자가 틀린 것이 몇 개 있다(`딸기바나나주스` → `딸기비니나주스`, `망고요거트스무디` → `랑고요거트스무디`). 사용자가 목록에서 고르는 용도라 쓸 만하지만, 글자가 틀리면 목표 문장이 어색해질 수 있다.
- 시간은 5~7초다. 안내(`/api/guide`)보다 느리지만 목표를 정할 때 한 번만 부르므로 허용 범위로 본다.

## 3. 바꿀 문구

`buildMenuMessages`의 `system` 배열을 아래로 바꾼다. 시험한 문구 그대로다.

```ts
const system = [
  "너는 키오스크 앞에서 주문을 어려워하는 사람(고령자, 저시력자, 외국인)을 돕는 안내원이다.",
  "사진은 키오스크의 메뉴 화면이다. 화면에 보이는 메뉴 상품을 모두 items에 담는다.",
  "items의 각 항목은 { name, price }이다. name은 상품 사진 아래에 적힌 이름을 바꾸지 말고 그대로 쓰고, price는 그 아래 가격(예: 3,900원)이다.",
  `위에서 아래로, 왼쪽에서 오른쪽 순서로 읽고 최대 ${MAX_MENU_ITEMS}개까지 쓴다.`,
  "위쪽의 탭(커피, 음료 등), 아래쪽 장바구니·결제하기 같은 버튼은 메뉴가 아니므로 넣지 않는다.",
  "글자가 일부 가려져도 읽을 수 있는 메뉴는 넣는다. items를 비우는 것은 메뉴가 하나도 안 보일 때뿐이다.",
  "message에는 메뉴 이름을 나열하지 말고, '메뉴가 여러 개 보여요. 원하는 것을 하나 골라 주세요.'처럼 짧게 쓴다.",
].join("\n");

return [
  { role: "system", content: system },
  { role: "user", content: "이 메뉴 화면에서 주문할 수 있는 메뉴를 모두 읽어 줘.", images: [req.image] },
];
```

바뀐 점은 네 가지다.

1. `items`를 비우는 조건을 "메뉴가 하나도 안 보일 때뿐"으로 좁혔다.
2. `message`에 메뉴 이름을 나열하지 못하게 했다. 이름은 `items`에만 들어간다.
3. 이름은 상품 사진 아래 글자를 그대로, 읽는 순서는 위→아래·왼쪽→오른쪽으로 정했다.
4. 탭과 장바구니·결제 버튼은 메뉴가 아니라고 명시했다.

시험하지 않은 것: 영어(`lang: "en"`) 응답. 한국어만 확인했다. `message`를 영어로 쓰게 하는 문구(`message는 ${answerLang}로 쓴다.`)는 기존 코드에 있던 줄을 그대로 두면 된다.

## 4. 함께 바꾸면 좋은 것

`lib/ollama.ts`의 `options`에 `num_predict: 900`을 더한다. 003번 사진처럼 모델이 같은 말을 반복하면 40초 넘게 걸리며 끝나지 않는데, 출력 길이를 제한하면 그 전에 끊긴다.

```ts
options: { temperature: 0, num_predict: 900 },
```

## 5. 사진 크기와 위치 좌표 (참고)

메뉴 읽기는 좌표를 쓰지 않아 영향이 작지만, 안내(`/api/guide`)의 위치는 보내는 사진 크기에 크게 좌우된다. Ollama는 사진을 안쪽에서 일정 크기로 바꾸고 모델은 그 크기 기준 좌표를 낸다. 작은 사진을 그대로 보내면 위치가 전부 어긋난다.

| 보낸 크기 | 버튼 정확도 | 위치 정확도 |
| --- | --- | --- |
| 긴 변 1024 이하로 줄임(지금) | 87.5% | 0% |
| 약 84만 픽셀 | 81.3% | 81.3% |
| 약 110만 픽셀 | 93.8% | 87.5% |

(7B, 16문항, 한 종류의 키오스크라 참고용 값이다.) `app/frame.ts`가 보내는 크기를 약 110만 픽셀로 키우는 것을 검토해 달라.
